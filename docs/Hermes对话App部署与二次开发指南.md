## 1. 这套东西是什么

一句话：**手机上的一个安卓聊天客户端，连你自己搭的 Hermes 网关，在手机上跟 AI 对话。**

它不是一个独立产品，而是 Hermes 的一个「前端外壳」。真正干活（跑模型、调工具、记记忆）的全在服务端，
手机这边只负责三件事：**把话发上去、把流式回复显示出来、把文件图片收发好**。

### 1.1 数据流

```
手机 App ──HTTPS──> 公网入口(域名/隧道) ──> 自建服务器
                                              └─ Hermes 网关
                                                   └─ api_server 平台（HTTP 接口）
                                                        └─ 模型 / 工具 / 记忆
```

### 1.2 为什么值得做成 App 而不是用网页

- 网页版在手机上锁屏就断，长任务（跑十几分钟的那种）直接丢；
- 原生 App 能挂前台服务保住连接，能发系统通知，能后台续接；
- 能自更新，改完一版手机点一下就升级，不用每次插数据线。

### 1.3 技术栈（照这个版本配，别乱升）

| 组件 | 版本 | 说明 |
|---|---|---|
| 语言 | Kotlin | 全程 Kotlin + Jetpack Compose |
| UI | Jetpack Compose (Material3) | 单 Activity，无 XML 布局 |
| 网络 | OkHttp 4.12.0 | REST + SSE 流式（手写 event-stream 解析） |
| 图片 | Coil 2.6.0 | 加载与显示 |
| 构建 | Gradle 8.9 + AGP 8.5.2 | |
| Kotlin 编译器插件 | 1.5.14 | 与 Compose 版本必须配套 |
| Compose BOM | 2024.06.00 | |
| JDK | 17（编译目标）/ 21（运行时） | 见第 4 章说明 |
| minSdk / targetSdk | 26 / 34 | |

## 2. 环境准备（你要先有什么）

### 2.1 服务端要有

- 一台能跑 Hermes 的 Linux（本机 / 容器 / 云主机都行），**建议 ≥4GB 内存**；
- 一个能访问到它的通道：公网域名 + 反代、Cloudflare Tunnel、SSH 反向隧道、内网直连——**任选其一**；
- Hermes 已装好并能正常对话（这个 App 只是外壳，网关本身不通的话 App 什么也做不了）。

### 2.2 构建机要有（编 APK 的那台机器）

| 需要 | 建议做法 | 注意 |
|---|---|---|
| JDK | 装 JDK 17 或 21 | 系统 `java -version` 能出结果 |
| Gradle 8.9 | **直接解压 zip**，不用包管理器 | 版本必须 8.9，高了低了都可能翻车 |
| Android SDK | 只装三样：`platform-tools`、`platforms;android-34`、`build-tools;34.0.0` | 见下方脚本 |
| 磁盘 | 预留 ≥15GB | Gradle 缓存 + SDK 很大 |
| 内存 | 构建时峰值约 2GB | 见 `gradle.properties` 的 `-Xmx2048m` |

**接受 Android SDK 许可**（不做这步编译一定卡）：

```bash
yes | sdkmanager --licenses
```

**参考安装脚本**（按你自己的目录改）：

```bash
export JAVA_HOME=<你的 JDK 路径>
export ANDROID_SDK_ROOT=<你的 SDK 目录>
export ANDROID_HOME=$ANDROID_SDK_ROOT
export PATH=$JAVA_HOME/bin:$ANDROID_HOME/cmdline-tools/latest/bin:$ANDROID_HOME/platform-tools:$PATH

# 解压 cmdline-tools 到 $ANDROID_HOME/cmdline-tools/latest
# 然后：
yes | sdkmanager --licenses
sdkmanager --install "platform-tools" "platforms;android-34" "build-tools;34.0.0"
```

> **国内网络提示**：`sdkmanager` 首次要从 Google 下载 platform 和 build-tools，直连很慢甚至超时。
> 若你有代理，给这台机器配上（本机做法是让构建机的流量走一个本地代理端口）；
> 或者先用能通的机器下好再拷过来。

### 2.3 手机要有

- 安卓 8.0（API 26）以上；
- 允许安装未知来源应用（自更新必需）。

## 3. 服务端：Hermes 网关侧

### 3.1 打开 api_server 平台

Hermes 网关自带的 `api_server` 就是 App 的接口层，默认**只监听 127.0.0.1:8642**。

- 只在本机反代 → 保持默认即可；
- 要让**另一台机器**直接访问（内网直连场景）→ 必须把监听改成 `0.0.0.0`：

```bash
# 在 Hermes 的 .env 里（路径通常是 <HERMES_HOME>/.env）
API_SERVER_HOST=0.0.0.0
```

**改完必须重启网关才生效**（这个值是启动时读的，不是热加载）。

### 3.2 认证：一把 key 管一个 profile

App 每个请求都带 `Authorization: Bearer <API_SERVER_KEY>`。

**最容易踩的坑**：如果一台网关同时服务多个 profile（比如你自己一个、给朋友一个），鉴权是按
**URL 前缀**分的：

| 请求路径 | 用哪把 key |
|---|---|
| `/v1/runs`、`/api/sessions`（不带前缀） | default profile 的 key |
| `/p/friend/v1/runs`、`/p/friend/api/jobs` | friend profile 的 key |

拿 A 的 key 请求 B 的路径 → **401**。这不是接口不存在、也不是 key 写错，别据此下结论。

### 3.3 服务端补丁（App 的部分功能依赖它）

**先分清哪些是上游 Hermes 原生、哪些是补丁加的**，别以为拿了 App 源码就什么都能用：

| 能力 | 来源 | 不打补丁会怎样 |
|---|---|---|
| 对话、SSE 流、审批/澄清、定时任务、上传附件、图片收发 | **上游 Hermes 原生** | 正常可用 |
| 收非图片附件（.zip/.pdf/.md 等内联成卡片） | **补丁 A** `apply_media_file_patch.py` | 非图片回复只显示成一行纯文本路径，卡片出不来 |
| 8MB 以上大文件走网关托管、按需下载 | **补丁 B** `apply_media_host_patch.py` | 大文件整块塞进消息体，可能失败 |
| 耗时以服务端为准（数字稳定） | **补丁 C** `apply_run_duration_patch.py` | App 回落到本地掐表，数字偏大且不稳定 |

三个补丁脚本都在包内 `patches/` 目录，**幂等**：已经打过就打印「跳过」，锚点找不到就报失败（不会硬改）。

**用之前必改一处**：三个脚本里都写死了目标路径
`/usr/local/lib/hermes-agent/gateway/platforms/...`——那是本机的网关安装路径。
你的 Hermes 装在别处，就把脚本顶部那个路径改成你自己的（通常在 Hermes 的 `lib/hermes-agent/` 下）。

跑法：

```bash
python3 patches/apply_media_file_patch.py
python3 patches/apply_media_host_patch.py
python3 patches/apply_run_duration_patch.py
```

**升级 Hermes 会把这些补丁冲掉**，每次升级后重跑一遍即可。

> 判断补丁有没有生效，**不是看文件里有没有那段代码**，而是**比对补丁文件 mtime 和网关进程启动时间**：
> 补丁晚于进程启动 = 还没生效，必须重启网关。

### 3.4 反向隧道（如果你用隧道暴露服务）

用 SSH 反向隧道（`ssh -R`）把内网 8642/8644 打到公网机器时，有一个**必知的坑**：

**隧道会「进程还活着、但转发通道已经死了」。** 因为它探活的是「对面机器在不在」，对面一直在线，
所以进程永远不退出，`Restart=always` 也救不了——系统认为它没崩。

**根治办法 = 加一个纯脚本看门狗**（不消耗 token）：
每 5 分钟从外部探一次 `/health`，同一轮隔 15 秒探两次，**两次都失败才动手重启隧道**，
带冷却时间和连续失败上限。别用「一次失败就重启」，会被网络抖动误触发。

## 4. 客户端：把安卓工程编出 APK

### 4.1 关键前提：这个工程**没有 gradle wrapper**

也就是说，**没有 `gradlew`**。照着网上教程敲 `./gradlew assembleDebug` 会 `command not found`。
本工程走的是仓库根的 `build.sh`，里面固化了工具链路径。

### 4.2 先改三处，让它适配你的机器

| 文件 | 改什么 |
|---|---|
| `build.sh` | 三个环境变量：`JAVA_HOME` / `ANDROID_SDK_ROOT` / `ANDROID_HOME`，以及 `GRADLE` 的绝对路径 |
| `local.properties` | `sdk.dir=<你的 SDK 路径>`（**这个文件不入库，换机器必须自己补**） |
| `settings.gradle.kts` | 仓库镜像按你的网络情况调（见 4.4） |

### 4.3 一键构建

```bash
cd <项目目录>
./build.sh          # 编译 debug 包
./build.sh clean    # 先清理再编
```

产物：`app/build/outputs/apk/debug/app-debug.apk`
日志：`build.log`

**判断成功看两样同时出现**：日志里的 `BUILD SUCCESSFUL` **和** 脚本末尾的 `EXIT=0`。
只看其中一个不够——有时编译成功了但脚本因为别的原因返回非零。

### 4.4 依赖下载慢怎么办

`settings.gradle.kts` 里仓库顺序是**国内镜像优先**，然后才回落官方源：

```
阿里云 gradle-plugin → 阿里云 google → 阿里云 public → google() → mavenCentral()
```

国内直连 Google Maven 很慢，**这个镜像优先的顺序是刻意配的，别删**。
如果你在墙外，反而可以把它调过来。

### 4.5 构建超时 ≠ 构建失败

首次全量编译可能超过工具的等待窗口被报 timeout，但 **Gradle 进程会把包编完**。
超时后**先查产物文件的修改时间**，不要盲目重跑：

```bash
ls -l app/build/outputs/apk/debug/app-debug.apk
# 或者看 build.log 尾部有没有 BUILD SUCCESSFUL
```

重跑一轮纯属浪费几分钟。

### 4.6 签名（很重要，关系到能不能装上）

本工程**release 也直接签 debug 密钥**（`signingConfig = signingConfigs.getByName("debug")`），
用的是 `~/.android/debug.keystore`。

含义：

- **换机器构建，必须带上同一个 `debug.keystore`**，否则新旧包签名不一致，
  手机装新包时会报「应用未安装 / 签名冲突」；
- 自用够用，不追求上架；真要独立签名就自己建 keystore 并改 `build.gradle.kts`。

## 5. 发布与自更新链路

App 的「检查更新」是**拉一个 JSON 清单**，比对版本号后下载 APK 并拉起系统安装。

### 5.1 清单长这样

```json
{
  "versionCode": 82,
  "versionName": "2.71",
  "url": "https://<你的更新域名>/update/<文件名>.apk",
  "notes": "这一版改了什么",
  "size": 16284223,
  "md5": "xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx"
}
```

### 5.2 发布五步

1. 改 `app/build.gradle.kts` 的 `versionCode`（**必须递增**）和 `versionName`；
2. `./build.sh` 出包；
3. 把 APK 拷进 `dist/update/`，命名 `<名>-<版本>-<md5前8>.apk`；
4. 更新 `dist/update/version.json`：`size` 用 `stat -c%s`、`md5` 用 `md5sum` 取实际值；
5. **不需要重启任何服务**——更新分发就是一个静态文件服务（`python3 -m http.server`），直接读盘。

### 5.3 公网链路与 CDN 缓存（第二个大坑）

如果更新分发走 CDN（Cloudflare / EdgeOne / 各种加速），**CDN 会缓存 version.json**。

症状：本地 `curl 127.0.0.1:<端口>/update/version.json` 已经是新版，
但 `curl https://<更新域名>/update/version.json` **还是旧版**，响应头带 `eo-cache-status: HIT`
之类 —— 此时手机点「检查更新」拿到的还是旧版本号，**等于没发出去**。

判断与处置：

- 加随机参数能拿到新版 → 证明只是缓存挡着，不是源站没更新：
  ```bash
  curl "https://<更新域名>/update/version.json?t=$RANDOM"
  ```
- 根治 = **让 App 的检查更新请求自带防缓存参数**（URL 后拼时间戳），一次改动以后不用再管；
- 临时处置 = 去 CDN 控制台按路径刷新（几秒），或等自然过期。

### 5.4 发布收尾必须做的两件事

**① 完整下载一次对 md5。** 别只信 `curl -sI` 的 `content-length`（那只证明头对，证不了内容对）：

```bash
curl -s "https://<更新域名>/update/<文件>.apk?t=$RANDOM" -o /tmp/x.apk
md5sum /tmp/x.apk        # 与本地发布文件的 md5 一致才算真发出去
```

**② 客户端「点检查更新」拉的就是这份**，所以缓存挡没挡住也一并排掉了。

> **CDN 偶发 5xx 不代表文件坏了**：边缘节点对单次请求误拦是常事，紧接着的 `curl -sI` 正常返 200
> 就说明没问题。判据 = **状态码 + 实际下载回文件的 md5**，别据此重编重发。

## 6. 完整落地顺序（从零到能用）

按这个顺序做，每一步都能独立验证，出问题好定位：

1. **服务端先通**：Hermes 网关能正常对话（先用命令行或网页确认）；
2. **开 api_server**：确认本机 `curl http://127.0.0.1:8642/health` 返回正常；
3. **打通公网**：从外部网络 `curl https://<你的域名>/health`，返回正常；
4. **编译客户端**：改好三处路径，`./build.sh` 出 APK；
5. **填客户端配置**：改 `Keys.kt` 里的服务器地址、更新地址、你的 key（**用你自己的，别抄任何人的**）；
6. **装机实测**：手动装 APK，能登录、能收发消息；
7. **再配更新链路**：架好静态文件服务 → 出第二版 → 手机上点「检查更新」能升上去；
8. **最后打服务端补丁**（如果你需要文件收发 / 精准耗时）。

## 7. 踩坑指南（重点）

下面每一条都是真实踩过的，按「现象 → 原因 → 处置」写。**建议先通读一遍再动手**。

### 7.1 构建类

| 现象 | 原因 / 处置 |
|---|---|
| `gradle: command not found` | 没用全路径。跑 `./build.sh`，或把 Gradle 加进 PATH |
| `SDK location not found` | `ANDROID_HOME` 没导出，或 `local.properties` 缺失（该文件不入库，换机器要自己补） |
| `licenses not accepted` | 重跑 `yes \| sdkmanager --licenses` |
| 编译卡在下载依赖 | 确认镜像仓库在 `settings.gradle.kts` 里且没被改掉 |
| 手机装新包报签名冲突 | 构建机换了 / keystore 丢了，用同一份重编 |
| 构建报 timeout | 多半是**假失败**，先查产物 mtime，别盲目重跑 |
| 报 `Unclosed comment` + `Missing '}'` | **Kotlin 块注释可以嵌套**。在 `/** ... */` 里写了 `/*`（比如注释里写「图片走 image 路径」带了个斜杠星号），会再开一层注释，末尾只关里层，外层一路吃到文件尾。注释里要写通配符就改行注释 `//` |

### 7.2 代码改动类

| 现象 | 原因 / 处置 |
|---|---|
| 一次改十几处，只有第一处生效 | **同批次多个 `patch` 会静默丢**，只有第一条保证落地且不报错。每个符号/函数一个独立 patch，改完立刻编译回读 |
| 大文件上 patch 报「路径被截断」 | 2000 行以上的文件用 patch 偶发此问题。改用脚本：读全文 → 确认唯一命中 → 替换 → 写回，并打印命中数 |
| 一堆不相干的 `Unresolved reference` | **连锁报错别追**。根因通常是**先报错的那个文件**结构断了。先修先报错的，不要去改被连累的文件 |
| 新加的 data class 引发全局报错 | 定义漏落了。先补定义再看剩余报错 |
| 正则匹配不到 | Kotlin 字符串里的正则别多转义。源码里写两个反斜杠，写四个就变成匹配字面反斜杠。落盘后回读原文确认 |
| 改主题/资源后没效果 | 升 `versionCode`，手机端有缓存 |

### 7.3 网络与连接类（最折腾人的一类）

**① 消息发出去一直转圈、永远不重连**

根因：SSE 流用了一个 `readTimeout=0`（无限长）的 HTTP 客户端。
连接「半死」时（连接还在、对面不回包），那条流会永久挂着，永远不触发重连。

**处置：必须用三个独立的客户端。**

| 用途 | 超时设置 | 为什么 |
|---|---|---|
| 普通 REST 调用 | `readTimeout=0` | 长任务要等 |
| **在线探针** | 硬性总超时（6 秒左右） | 复用长超时客户端会导致「掉线了还显示在线」——探针卡死，状态冻结在最后一次结果 |
| **SSE 事件流** | 读取超时设硬阈值（30 秒） | 服务端每 10 秒必发一个心跳帧，30 秒 = 3 个心跳周期，正常空闲不误杀，真假死时准时抛超时交给上层重连 |

**② 断线后绝对不能伪造用户消息**

早期的错误做法：SSE 断开时，自动往会话里塞一条「继续」当作用户输入。
后果是**用户会看到自己从没发过的消息**。

**正确做法**：断线时去查同一个 run 的状态——
- 还在跑 → 续接**同一个 run** 的事件流，不新增任何用户消息；
- 已结束 → 拉回服务端产出。

**③ 重连要用退避，不能固定短间隔猛试**

固定「1.2 秒 × 3 次」= 4 秒内烧完就彻底放弃。
正确做法是指数退避（1s、2s、4s、8s……封顶 30s），最多重试 8 次左右。
**收到任意正常事件就把重试计数归零**。

**④ 防重入必须用原子量**

「一次断流触发多条恢复链」是这类 App 最反复的一类缺陷。症状：同一条日志一次打好几遍、
请求成倍、一边判「还在跑」一边判「已结束」互相打架。

- 别用普通 `Boolean` 做防重入标记（并发时两个线程都读到 `false` 就各自起一条循环）；
- 一律用 `AtomicBoolean.compareAndSet(false, true)`；
- **每个提前退出都要留一行日志**，否则排查时日志里只剩「第 N 次重试」没有「探测结果」，会被误读成卡死。

**⑤ 判断「还在跑」的状态集合必须与服务端逐字对齐**

漏一个等待态（比如「等待用户澄清」）的后果不是「少判一次」，而是
**断流期间服务端正在等你回应时，被客户端判成「任务已结束」**——卡片挂不上、流也不再续接，
用户以为任务丢了。改任何状态机时，先把服务端所有状态值列出来逐个对。

### 7.4 消息落盘与刷新类

**核心判据：一个字段要不要落盘，看它会不会被「重进 App 后的恢复逻辑」重建。会被重建的，不落盘就等于每次重进都重新初始化。**

| 现象 | 原因 / 处置 |
|---|---|
| token 用量 / 耗时重开 App 就没了 | 落盘函数**没存这个字段**，读回时被丢；或者从服务端刷新时，合并逻辑用「服务端没有这份数据」把本地那份覆盖掉了。两处都要改：**存它** + **合并时加守卫**（服务端那条没有就保留本地） |
| 只发了图/文件没打字，消息重开就消失 | 落盘的丢弃条件只查了「正文 + 工具轨迹」。判据要加上「图片 / 附件 / 待办卡片」——**正文为空但有载荷的消息**是同一个坑 |
| 待办卡片（审批/澄清）重启后不见了 | 三个原因：① 探测 run 时只取了状态字符串，**把载荷对象扔了**；② 卡片气泡正文往往是空的，被落盘过滤掉；③ 挂载位置没考虑「重启后消息的 pending 已归 false」 |
| 耗时显示不准（实时 2 分、最终 1.7 分） | **两个计时起点打架**。同一语义的时间戳只允许有一个写入点。看到「最终值总比实时值小一截」就先数一数 `startedAt =` 写了几次 |
| 压缩后回复贴错气泡 | 历史合并按「第几条用户消息」对齐，删行后整段错位。正解 = 按「用户消息正文归一 + 时间窗口」做顺序匹配 |

**耗时显示的额外要求**（用户明确提过）：
- 必须**执行中实时跳动**，不是跑完才给一个死数；
- 单位要自适应：1 分钟以内显示秒，到 1 分钟起显示分钟；
- 实时计时与最终耗时**共用同一个格式化函数**，别各写一份。

### 7.5 前台服务与通知类

| 现象 | 原因 / 处置 |
|---|---|
| 高版本安卓上崩，堆栈里只有系统的看不到自己代码 | `startForeground` 的异常被 `runCatching` 吞了。失败时进程既不退也不停，系统等约 10 秒判违约直接杀进程。**正解 = `try/catch`，失败时写故障留痕 + 干净退出**，从「崩溃」降级为「安静降级」 |
| 通知点了没反应 | **每条通知都必须挂 `contentIntent`**，漏挂不报错、通知照常显示，只是点击无响应，极易被误当成「系统限制」而放弃修。另外每条通知要用**不同的 requestCode**，否则会互相覆盖 |
| 后台被杀后通知全没了 | 前台服务的触发判据别跟「有没有任务在跑」绑，跟**用户的开关**绑 |

**通用检查：凡 catch 住异常又不留痕的地方，都是隐形崩溃源。**
特别是「前台服务启动失败」这种进程不死的错误，走不到未捕获异常处理器，
所以「上次闪退记录」永远看不到它——偏偏它才是真凶。要**单独留一份「服务故障记录」**。

### 7.6 文件与权限类

- 上传文件的 **MIME 必须按真实扩展名返回**，不能兜底成图片类型——
  服务端按 Content-Type 过白名单，填错类型等于传不上去；
- **「移动/删除原文件」的步骤，后面所有用到该文件的地方都要改用新路径**。
  曾经的 bug：函数把文件从 A 拷到 B 后删掉 A，但调用方仍拿 A 去读 → 附件必然发送失败；
- 分享文件出去，**FileProvider 的路径声明必须在 `res/xml/file_paths.xml` 里加一条**，
  不加会拒，分享出去是空文件或直接崩；
- 「一点就没、不可恢复」的入口（比如删除会话），**必须加二次确认**。
  问自己一句：误触了怎么办？

### 7.7 配置与部署类

| 现象 | 原因 / 处置 |
|---|---|
| 改了配置但行为没变 | 有些配置是**启动时读取**的（比如监听地址），必须重启服务；有些是**按文件签名缓存的**，调用时实时读。分清楚再动手 |
| 配置写错键路径不报错，只是没生效 | 很多配置工具写错键会**新建一个没人读的段**，不报错。改完**必须回读配置文件确认落点** |
| 升级后服务端改动消失 | 升级会冲掉补丁。**每次升级后重打**，并把补丁脚本归档 |
| 服务端补丁「打了但没生效」 | 判据不是「文件里有没有那段代码」，而是**比对补丁文件 mtime 与进程启动时间** |
| 重启服务的命令被拦 | 如果环境有安全护栏，直接在目标机器上操作，别隔着多层包装 |

### 7.8 界面类（这位用户对界面重量敏感）

- **输入框状态别放回聊天页**：放回去就退回「打字卡顿」的版本。
  正确做法是把输入状态提到外层，打字只让输入栏重组，消息列表完全不动；
- **草稿去抖落盘**：停手 600ms 才写，长文本每次按键写盘会反复整串序列化；
- **浅色模式必须整套换色，不能只换背景**，否则黑背景黑字；
- **凡是要给用户一个「点一下」的控件，默认走图标而非文字按钮**；
- **待发区的图片和文件要区分显示**（图片缩略图 / 文件卡片），气泡回显同理；
- **服务端返回的一切英文标识都要在客户端翻译**（任务名、状态、排期表达式等）。
  翻译表要写成**「精确名 + 关键词兜底」**，不能只写死自己这边的名字，
  否则换个 profile、加个新任务就认不出、当场回落显示英文；
- **配色判断要用原始布尔值，不要用翻译后的字符串比较**——翻译一改配色就悄悄失效。

## 8. 二次开发：改代码的纪律

### 8.1 动手前

1. **先同步**：`git pull`（多人共用一个工作副本时尤其重要）；
2. **读设计文档**：先看 `docs/DESIGN.md`（有哪些文件）和 `docs/INTERNALS.md`（运行时怎么跑、哪些地方踩过坑）；
3. **确认「上一版」是哪一版**：三处对齐才算——
   ```bash
   git log --oneline -2
   grep versionCode app/build.gradle.kts
   cat dist/update/version.json
   ```
   **发版前必须回读当前值再递增，不能凭记忆**（同一工作副本可能被别人刚占用掉下一个号，撞号就跳）。

### 8.2 改的时候

- **一个提交一个主题**，别把不相关的改动混在一起；
- `git status` 里若出现**不属于本批主题的改动**（别人正在写的文件），
  只 `git add` 自己那几个文件，**绝不用 `git add -A`** 顺手带走；
- **版本号 / versionName / version.json 只由发布的那一个人改**，两个人别并发改这三个字段。

### 8.3 改完

1. 立刻编译（`./build.sh`）——**脚本说「都替换了」只证明文本落盘，证明不了编译得过**；
2. 同步文档：功能变了写 CHANGELOG，设计变了改 DESIGN；
3. 推回共享仓库。

### 8.4 发布检查单

- [ ] `./build.sh` 出 `BUILD SUCCESSFUL` / `EXIT=0`
- [ ] `versionCode` 递增且与 `version.json` 一致
- [ ] APK 已进 `dist/update/`，`size` / `md5` 与实际文件一致
- [ ] `notes` 写清了这一版变化（**键名必须是客户端解析的那个**，写错弹窗就是空的）
- [ ] 本地源站与公网入口都 curl 过，公网这次是 `MISS` 不是 `HIT`
- [ ] 完整下载一次对过 md5
- [ ] 改动已 commit 并 push
- [ ] 手机端实测：能更新、能登录、能收发消息

### 8.5 回滚

```bash
git log --oneline          # 找上一个好的提交
git revert <hash>          # 或 git reset --hard <hash>
```

**APK 回滚更简单**：旧包都留在 `dist/update/` 不会自动删，把 `version.json` 指回旧 APK 即可。

## 9. 常见故障速查表

### 9.1 「手机上连不上」

**按这个顺序只读定位，别一上来就重启隧道。**

```bash
# 1. 服务端本机端口在不在听
ss -tlnp | grep <端口>

# 2. 本机健康检查
curl -s -o /dev/null -w '%{http_code}' -m 6 http://127.0.0.1:<端口>/health

# 3. 网关服务状态
systemctl is-active <网关服务名>
journalctl -u <网关服务名> -n 30 --no-pager | grep -i api_server

# 4. 公网路径（App 实际走的）
curl -s -o /dev/null -w '%{http_code} %{time_total}' -m 20 https://<域名>/health
```

判据：

- **本机端口没监听** → 根因在网关，不在隧道。
  **隧道只是受害者**：它日志里刷「连接被拒」就是「后端没监听」，此时重启隧道无效，
  必须先把 api_server 救起来；
- 本机通、公网超时 → 才是隧道问题；
- **对话接口超时但更新接口正常** → 这是**两条独立通道**。更新能用不代表对话能用，别被误导。

**特别注意**：api_server 启动失败会被网关吞掉——网关进程状态是 `active`，
其他平台（比如微信）照常工作，但端口根本没监听。**只看服务状态会误判成「一切正常」**，
必须查监听端口和日志。

### 9.2 「历史对话不见了」

**先分清楚是服务端丢了还是手机本地丢了，别一上来就查服务端。**

- 服务端真相在网关的数据库里，`GET /api/sessions` 读的就是它；
- **App 的「历史对话」列表读的是手机本地索引**，不是服务端会话列表。

由此两条重要结论：

1. **服务端一条没丢 ≠ App 列表不空**，两者是两套数据；
2. **App 列表从不显示别的端（微信/命令行）建的会话**——那些会话从没写进手机本地索引。
   **这是设计缺口，不是故障**。

列表「看着空了」的常见原因：清缓存/重装 App（本地索引没了）、换手机、**profile 切错**
（读到了另一个 profile 的索引文件）。

**修「列表空」时的一个大坑**：别改成「启动就把服务端会话全灌进本地」。
实测这么做过一次，灌进了几十条测试会话和老会话，用户立刻反馈「历史对话召回太多了」。

正确形态：

- 平时（本地列表非空）**一条都不自动补**，只同步已有行的标题；
- 仅当本地列表整个为空才自动补，**且加门槛**（最近 7 天、消息数 ≥6）；
- 想看别的端会话时，给一个**显式「拉取」按钮**手动合并。

> **通用教训：任何「从服务端补内容进用户可见列表」的自动行为，都必须有时间/条数门槛，
> 且优先做成用户显式触发。用户对列表变长的容忍度远低于预期。**

### 9.3 「插话插不进去」

先查服务端日志里那条请求的返回码：

- **返回 200** → 服务端收下了，问题在客户端**没有给可见反馈**（不是发送失败）；
- 服务端只在 run 状态为「运行中」时接受插话，其他状态返回 409——
  所以「等你确认/等你选一下」期间插话会被拒，按钮语义上应只在本轮正在流式输出时才给；
- **注入时机是「下一批工具调用之后」**，不是立刻。如果 agent 已经收尾、不再调工具，
  这句话就进不了本轮——这时要**接住服务端回传的未送达文本，放回输入框**，不能静默丢。

### 9.4 「任务跑完不响 / 不播语音」

按这个顺序查，**每一步都拿到实测证据再往下走**（反过来查会把「没更新」误诊成「代码坏了」）：

1. **服务端到底出没出语音**：别读代码推断，直接发一条真请求，看回复里有没有音频附件；
2. **客户端的识别正则能不能匹配上那段输出**：拿第 1 步的真实输出跑一遍等价正则；
3. **只剩开关**：到这一步服务端与解析层都自证清白了，问题在手机上那个开关的状态。

**关键坑：开关是系统偏好存储，覆盖安装会原样保留、不会因新版本改了默认值而重置。**
所以「新版把默认值改成开」**只对全新安装生效**；从旧版一路升上来的机器，
只要那个键被写过一次（哪怕是被误点），升级后仍然是旧值。
改动开关默认值时**必须在回复里说清这一条**，否则用户升完发现没变化会以为改动没生效。

### 10.3 两条最重要的原则（如果只记两条，记这两条）

**一、绝不伪造用户消息。** 任何断线/重试/续接逻辑，都不许往会话里塞一条用户没发过的输入。
这是所有「用户看到自己没说过的话」类 bug 的总根因。

**二、任何自动往用户可见列表/界面补内容的逻辑，都必须有门槛，且优先做成用户显式触发。**
用户对「东西自己变多」的容忍度，远低于开发者的预期。
